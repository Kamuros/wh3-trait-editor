## Critical findings

No Critical failure was reproduced. This is not proof that arbitrary saves are safe. Game-level correctness remains unverified, and the incomplete real-save corpus is a material limitation.

## High findings

### H1 — Final verification accepted unrelated byte changes — fixed

**Evidence:** baseline [js/savefile.js:211](https://github.com/Kamuros/wh3-trait-editor/blob/e9aca7d/js/savefile.js#L211) compared character count, innate keys and paths, without comparing the rest of the file. A synthetic no-edit output with byte 4 changed passed with an empty problem list. This confirms a verifier blind spot, not that the normal exporter had already corrupted a game save.

**Impact:** unrelated changes from a parser/rebuilder defect could be reported as verified and go unnoticed.

**Patch:** [js/savefile.js:231](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L231) now checks complete bytes in each logical container. It applies only requested field changes and permitted compressed-stream/length replacements to an expected copy, then compares it with the output. A no-edit output must equal the original file exactly.

**Validation:** 128 seeded cases plus two fixed fixtures reject unrelated header changes. The real-save test changes exactly four byte values within two selected four-byte references in the decompressed campaign. All other campaign bytes remain identical.

### H2 — Unknown patches and partially parsed records could still be edited — fixed conservatively

**Evidence:** baseline [js/esf.js:62](https://github.com/Kamuros/wh3-trait-editor/blob/e9aca7d/js/esf.js#L62) checked only the container magic. Baseline [js/savefile.js:199](https://github.com/Kamuros/wh3-trait-editor/blob/e9aca7d/js/savefile.js#L199) did not gate editing by game version or parser diagnostics. Unknown nodes were skipped and their records could still contribute previously captured trait keys.

**Impact:** inferred schema changes between game versions could produce a plausible-looking but incorrect character/trait mapping. No such cross-version game failure was reproduced because only one version was supplied.

**Patch:** [js/savefile.js:71](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L71) records version labels and makes unknown/mismatched builds or incomplete parsing read-only. Only the observed `v9.0.5 Build 51143.4399233` is editable; this is a structural-test allowlist, not a guarantee of game or mod compatibility. The core build method enforces the block at [js/savefile.js:217](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L217).

**Validation:** synthetic v9.0.6 is readable but editing rejects; no-edit export remains byte-identical. Unknown signatures and oversized/truncated varints reject.

### H3 — Advanced grouping could offer another subtype’s traits — fixed

**Evidence:** baseline [js/app.js:38](https://github.com/Kamuros/wh3-trait-editor/blob/e9aca7d/js/app.js#L38) exposed every candidate field. Baseline [js/savefile.js:131](https://github.com/Kamuros/wh3-trait-editor/blob/e9aca7d/js/savefile.js#L131) grouped by whichever field was selected. Selecting a faction field groups different agent subtypes together, permitting cross-subtype choices even though the UI calls them alternatives for the same character type.

**Impact:** a user could unknowingly assign a trait observed only on another subtype. This is a confirmed code-path problem; actual game rejection/effects are inferred.

**Patch:** editable grouping is restricted to the observed field 13. Both [optionsFor, js/savefile.js:161](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L161) and [build, js/savefile.js:219](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L219) enforce subtype membership. Other candidate options are disabled.

**Validation:** alternate grouping produces no edit choices; unobserved keys are rejected by the core builder.

### H4 — In-game trait eligibility/effects remain inferred — open, conditional High risk

**Evidence:** [js/savefile.js:147](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L147) derives pools from observed characters, not game database restrictions; [js/savefile.js:201](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/savefile.js#L201) writes existing string indices. No code updates or verifies game-calculated effects or mod-specific caches.

**Trigger/impact:** if a DLC/mod restricts a trait further than subtype, or caches effects elsewhere, structurally correct output could have incorrect effects that the user does not notice. This is an inferred risk, not a reproduced failure; the severity is conditional on that behavior.

**Why not patched:** determining those rules needs game database exports, mod-specific evidence and in-game testing. Inventing them would create a larger risk. The UI explains the observed-pool limit and requires checking results in game. Resolution requires matching the displayed trait and effects after load, end-turn, save and reload, across a documented compatibility matrix.

## Security/privacy checklist

- **CSP:** added restrictive meta policy with `connect-src 'none'`, self-hosted scripts/styles, no objects, forms or base changes. [index.html:5](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/index.html#L5). Not equivalent to every response-header protection.
- **Third-party/SRI:** existing fzstd 0.1.1 remains locally bundled and MIT-licensed; SHA-384 integrity added. [index.html:75](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/index.html#L75). SRI does not protect against an attacker who can change both HTML and the hash.
- **Telemetry/error reporting:** no app telemetry or remote error service found. Errors go to the local console. Browser test observed only local page/asset requests, no save/translation uploads. GitHub Pages may log normal site visits; this is separate from save contents.
- **Browser persistence:** no localStorage/sessionStorage/IndexedDB/cookie persistence in application code; tested storage remained empty. Download Blob URLs are revoked on replacement/clear; page termination also releases them. The browser’s downloads/history are outside the app’s storage policy.
- **XSS:** values are rendered with `textContent`, not HTML. A hostile name containing an image/onerror payload rendered as literal text; no element or script ran. [js/app.js:94](https://github.com/Kamuros/wh3-trait-editor/blob/45d5fe5f2bd46ad41320d008f19a0e9289f1bfdb/js/app.js#L94). This is a tested attack case, not a complete security proof.

## Tests and performance thresholds

Commands: `node tests/esf-format.cjs`, `node tests/player-faction.cjs`, `node tests/localisation.cjs`, `node tests/roundtrip.cjs`. All passed. Golden fixture hashes are recorded in the manifest. Seeded tests use 64 seeds for each container signature, without a new property-testing dependency. No real save is checked into fixtures.

Real-save checks: no-edit byte identity, edited campaign byte diff, unchanged scanner counts, player-faction selection, export/reparse, and byte-identical download retry. Browser checks also covered visible progress, disabled controls, forced failure recovery, translation import, per-field revert, XSS payload rendering, storage/network observations, and 320 px reflow.

Measured once after the final code changes using Chromium 156.0.8078.79 on Linux, Node 24.22.1; this is a shared cloud runner, not a controlled hardware benchmark:

| Metric | Target for reference workload (≤16 MiB input / ≤96 MiB expanded) | Observed |
| --- | --- | --- |
| Busy-state DOM feedback after click | ≤150 ms | ~1 ms; two animation frames explicitly allow a paint before work |
| Load | ≤10 s | 6.302 s |
| Build/verify/download request | ≤30 s | 15.168 s |
| Maximum main-thread task | ≤500 ms | 840 ms — target missed; two tasks exceeded 500 ms |

For larger accepted inputs, no completion-time guarantee is established. Hard limits are 64 MiB input, 256 MiB aggregate expanded bytes and eight containers, not a claim that every browser has enough RAM. Peak memory was not measured; malformed-pack resource exhaustion remains a separate open issue. Performance thresholds are engineering targets, not observed support for every file at the size limits.

Before declaring production compatibility: obtain an approved sanitized real-save corpus, test in-game effects and mod/DLC combinations, address remaining worker/memory limits, and perform assistive-technology testing.
